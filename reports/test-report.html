Problems found

Every failure in this run came from the tests, not from Minivora. The first four are fixed on the branch.

  • Smoke + dashboard scripts sent the wrong query parameterFixed in 17c2caa

    /api/v1/subdomains/check reads ?name=. smoke.js, load-dashboard-and-api.js and TC-ONB-002 used ?subdomain=, so every call returned 422.

  • Owner e2e spec asserted a heading that no longer existsFixed in 17c2caa

    The owner Today page greets by first name ("Good afternoon, E2E") and shows a "Store setup" card. The spec still expected "Welcome to <store>" and "Setup checklist". Store creation itself worked and reached /dashboard well under 60 s.

  • k6 CSRF helper sent the encrypted cookie in the wrong headerFixed: helper now uses X-XSRF-TOKEN for cookie values

    jsonHeaders() put the XSRF-TOKEN cookie value into X-CSRF-TOKEN, and the dashboard login sent it as _token. Laravel rejects both with 419, so every owner login and every checkout lead post failed, and the first dashboard run measured nothing.

  • Dashboard script logged in per virtual user, from one IPFixed: login in setup(), cookies kept

    Laravel's throttle:N,1 counts every throttled route against one per-IP key for guests. Owners who were already logged in called the throttled subdomain API, which pushed POST /login past its 20/min limit. The second run got 429 on 85 of 100 logins. Real owners each have their own IP. The script now logs each seeded owner in once in setup() and shares that session. It also set noCookiesReset, because k6 empties each virtual user's cookie jar every iteration by default and the session was dropped after one pass. A page that bounces to /login now counts as an error instead of a silent 200.

  • Shared per-IP rate limit between test suitesProcess note, no code change

    All test traffic comes from one IP. Running the smoke test right before the e2e suite exhausted the 60/min API limit, and the first e2e run got a 429 during store creation. The app behaved correctly. Leave about a minute between suites, or run e2e first.

How to read these numbers

Where it ran
  • A cloud container with 4 vCPUs and 15 GB of RAM
  • php artisan serve with 4 workers, SQLite, file cache and sessions
  • k6 on the same machine, so there's no network latency
What it does not prove
  • The numbers aren't from Hostinger. V-10 still needs an off-peak run against staging
  • MySQL, PHP-FPM and Cloudflare were not in the path
  • All traffic came from one IP, so per-IP limits are hit sooner than in real use
Not covered by this run
  • Manual cases in TEST_CASES.md (usability, Lighthouse, SUS)
  • AI evaluation set (V-09) against live LLM providers
  • Real payment gateways (test mode only, per V-04)
  • PHP worker memory over time. The sampler caught only the artisan serve launcher, so leak checks rest on the soak latency staying flat (p95 24 ms over 30 min)
